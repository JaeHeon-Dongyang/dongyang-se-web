# 동양구조엔지니어링 웹사이트 제작 마스터 프롬프트

당신은 시니어 웹서비스 기획자, UX/UI 디자이너, 프론트엔드·백엔드 아키텍트 역할을 함께 수행하는 개발 에이전트입니다.

Antigravity IDE의 현재 저장소에서 건축구조설계 및 안전점검·진단 전문기업인 **동양구조엔지니어링**의 공식 웹사이트를 기획하고 구현해 주세요.

이 프로젝트는 다음 기능을 결합한 간결하고 확장 가능한 기업 웹사이트입니다.

1. 회사와 전문성을 소개하는 공식 기업 웹사이트
2. 실제 제공 업무를 명확하게 설명하는 사업분야 페이지
3. 기술 문서와 PF3D 사용 매뉴얼을 제공하는 기술자료
4. 회사 정보, 위치 안내, 통합 문의 폼을 제공하는 문의하기
5. 향후 계산기, 안전점검 관리, 고객 포털 등 엔지니어링 도구를 추가할 수 있는 기반

모든 계획 문서와 사용자 화면은 한국어로 작성하고, 코드의 변수명·함수명·파일명은 일관된 영어로 작성해 주세요.

---

# 1. 작업 원칙

작업을 시작하기 전에 현재 저장소를 먼저 분석하세요.

- 기존 코드, 설정, 문서 및 폴더 구조 확인
- 사용 중인 프레임워크와 패키지 확인
- 기존 사용자 변경사항 보존
- 기존 코드가 있다면 불필요하게 다시 생성하지 않기
- 확정되지 않은 회사 정보나 기술 내용을 임의로 만들지 않기
- 실제 고객사나 수행 실적처럼 보이는 가상 정보를 만들지 않기
- 로고, 사진, 도면, 인증서 등 제공되지 않은 자산은 명확한 플레이스홀더로 처리
- 외부 사이트의 코드, 문구, 이미지, 로고를 복제하지 않기
- 비밀키, 계정 정보, 개인정보를 코드에 포함하지 않기
- 페이지 수를 늘리기보다 각 페이지의 완성도와 정보 전달력을 우선하기
- 콘텐츠가 없는 빈 섹션을 디자인을 채울 목적으로 노출하지 않기
- 구현 전에 요구사항, 아키텍처, 데이터 모델, 작업 순서와 완료 기준을 문서화하기
- 한 번에 전체 기능을 생성하지 말고 마일스톤별로 구현하고 검증하기

현재 저장소에 에이전트 규칙 파일이 있다면 해당 규칙을 준수하세요. 없다면 프로젝트에 적합한 `AGENTS.md` 또는 `CLAUDE.md`를 제안하세요.

# 6. 디자인 시스템

## 6.1 기본 색상

다음 색상을 기본 디자인 토큰으로 사용하세요.

```css
:root {
  --color-primary: #47b089;
  --color-primary-light: #ecf7f3;
  --color-background: #f9fafb;
  --color-surface: #ffffff;
  --color-heading: #16181d;
  --color-text: #686f7d;
}
```

색상 용도:

- `#47B089`: 링크, 아이콘, 선택 상태, 포커스, 강조 요소
- `#ECF7F3`: 강조 영역과 카드의 연한 배경
- `#F9FAFB`: 페이지 기본 배경
- `#16181D`: 제목, 핵심 텍스트, 강한 CTA
- `#686F7D`: 본문 및 보조 텍스트
- `#FFFFFF`: 카드 및 콘텐츠 표면

`#47B089` 배경 위 흰색 일반 텍스트는 충분한 명암비를 확보하지 못하므로 사용하지 마세요.

기본 CTA는 다음 중 접근성 기준을 만족하는 방식으로 설계하세요.

- `#16181D` 배경과 흰색 텍스트
- `#47B089` 배경과 `#16181D` 텍스트
- 흰색 텍스트를 사용할 수 있는 별도의 어두운 녹색 토큰 추가

Primary Hover, Primary Active, Border, Muted, Success, Warning, Error, Information, Disabled, Focus Ring 토큰도 정의하세요. 모든 텍스트와 UI 컨트롤은 WCAG 2.2 AA 명암비를 목표로 합니다.

## 6.2 타이포그래피

한글 가독성과 웹 성능을 고려한 산세리프 계열을 사용하세요. 특별한 제약이 없다면 Pretendard Variable과 적절한 시스템 폰트 fallback을 우선 검토하세요.

다음 토큰을 정의하세요.

- Display
- H1~H4
- Body Large
- Body
- Small
- Caption
- Label

제목과 본문의 크기, 굵기, 행간, 글자 간격을 일관되게 관리하고 본문의 한 줄 길이가 지나치게 길어지지 않도록 제한하세요.

## 6.3 레이아웃

# 7. 정보 구조

글로벌 내비게이션은 다음 5개 메뉴만 사용합니다.

```text
홈
회사소개
사업분야
기술자료
문의하기
```

전체 구조는 다음과 같습니다.

```text
홈
├─ 회사소개: 하위 메뉴가 없는 단일 랜딩페이지
├─ 사업분야: 4개 전문 분야를 소개하는 단일 랜딩페이지
├─ 기술자료
│  ├─ 기술자료 목록
│  └─ 기술자료 상세
│     └─ PF3D 사용 매뉴얼도 하나의 기술자료로 등록
└─ 문의하기
   ├─ 통합 문의 폼
   ├─ 회사 기본 정보
   └─ 주소 및 지도
```

다음 메뉴와 화면은 MVP에서 만들지 않습니다.

- 프로젝트 및 용역 실적
- 진행 중인 프로젝트
- 회사소개 하위 메뉴
- 인사말 독립 페이지
- 연혁 독립 페이지
- 전문 인력 독립 페이지
- 면허·인증·보유 기술 독립 페이지
- 기술 소식
- 독립 다운로드 메뉴
- FAQ
- PF3D 매뉴얼 최상위 또는 고정 하위 메뉴
- 문의 유형별 개별 페이지
- 채용

향후 확장 가능성만으로 빈 메뉴나 페이지를 미리 노출하지 마세요.

# 9. 페이지별 요구사항

## 9.1 홈페이지

홈페이지는 회사의 전문성과 네 가지 사업 분야를 빠르게 이해시키고 문의로 연결하는 역할을 합니다.

권장 구성:

1. 핵심 메시지와 CTA가 포함된 Hero
2. 짧은 회사 소개
3. 네 가지 사업 분야
4. 업무 방식 또는 핵심 가치
5. 주요 기술자료
6. 문의 CTA

프로젝트 실적이나 진행 중인 프로젝트 섹션은 넣지 마세요.

## 9.2 회사소개

회사소개는 여러 페이지로 분리하지 않고 현대적인 단일 랜딩페이지로 구성하세요.

권장 구성:

1. 회사소개 Hero
2. 회사를 설명하는 짧은 소개
3. 업무 원칙 또는 핵심 가치
4. 네 가지 전문 분야 요약
5. 회사 기본 정보
6. 문의하기 CTA

연혁, 대표 인사말, 조직도, 전문 인력, 면허·인증은 실제 콘텐츠가 제공되는 경우에만 페이지 내부의 간결한 섹션으로 추가하세요. 각각 독립 메뉴로 만들지 마세요.

## 9.3 사업분야

사업분야는 하나의 랜딩페이지에서 네 분야를 명확하게 구분해 설명하세요.

MVP 권장 URL:

```text
/services
/services#structural-design
/services#safety-inspection
/services#construction-safety
/services#demolition-review
```

각 분야의 설명 콘텐츠가 충분히 준비되었을 때만 상세 페이지 분리를 검토하세요.

## 9.4 문의하기

문의 유형별 페이지를 만들지 말고 한 페이지에서 모든 문의를 처리하세요.

권장 구성:

1. 간결한 문의 안내
2. 통합 문의 폼
3. 전화, 팩스, 이메일 등 회사 연락처
4. 주소
5. 지도 또는 외부 지도 연결

문의 유형은 폼의 선택 항목으로만 구분합니다.

- 사업 문의
- 기술 문의
- PF3D 문의
- 기타 문의

권장 필드:

- 문의 유형
- 이름
- 회사 또는 소속
- 전화번호
- 이메일
- 문의 제목
- 문의 내용
- 첨부파일
- 개인정보 수집 및 이용 동의

모든 문의는 `dy8000@daum.net`으로 전달할 수 있도록 설계하세요. 실제 이메일 발송 서비스와 인증 정보가 제공되지 않았다면 임의로 연동하지 말고 서버 측 발송 인터페이스, 필요한 환경변수, 연결 방법만 문서화하세요.

스팸 방지, 서버 측 입력 검증, 중복 제출 방지, 첨부파일 제한, 개인정보 보존 및 파기 정책을 고려하세요.

지도 공급자는 임의로 확정하지 말고 네이버 지도, 카카오맵, Google Maps의 국내 주소 표시와 운영 조건을 비교하세요. API 키가 없어도 주소와 외부 지도 링크로 위치를 확인할 수 있어야 합니다.

# 10. 기술자료와 PF3D 매뉴얼

## 10.1 기술자료 기본 구조

기술자료는 복잡한 포털이 아니라 목록과 상세 화면으로 구성된 명확한 콘텐츠 영역입니다.

권장 URL:

```text
/resources
/resources/[slug]
```

기술자료에는 다음 콘텐츠를 동일한 체계로 등록할 수 있어야 합니다.

- 기술 문서
- 기술 가이드
- 참고자료
- PF3D 사용 매뉴얼
- PDF나 양식이 첨부된 자료

기술 소식, FAQ, 다운로드를 별도 메뉴로 만들지 마세요. 다운로드 파일이 있다면 기술자료 상세 게시물의 첨부파일로 제공합니다.

기술자료 데이터 필드 예시:

```yaml
title:
slug:
summary:
category:
contentType:
thumbnail:
publishedAt:
updatedAt:
visibility:
featured:
keywords:
attachments:
seoTitle:
seoDescription:
```

첨부파일은 파일명, 형식, 크기, 설명, 버전, 등록일, 공개 범위, 다운로드 URL을 관리할 수 있도록 설계하세요.

## 10.2 PF3D 매뉴얼

PF3D 매뉴얼은 글로벌 메뉴나 기술자료의 고정 하위 메뉴가 아니라 **기술자료 목록에 등록되는 하나의 게시물**로 취급합니다.

목록 표시 예시:

```text
[프로그램 매뉴얼]
PF3D 사용 매뉴얼
PF3D의 설치, 모델링, 해석 및 결과 확인 방법을 안내합니다.
```

대표 URL:

```text
/resources/pf3d-manual
```

일반 기술자료와 같은 카드, 카테고리, 검색 및 콘텐츠 관리 체계를 사용하세요. 다만 매뉴얼 내용이 길어질 수 있으므로 상세 화면에서 다음 기능을 선택적으로 제공합니다.

- Markdown 또는 MDX 렌더링
- 문서 목차
- 제목별 앵커 링크
- 문서 내 검색
- PF3D 버전 표시
- 최종 수정일
- 이미지, 표, 코드, 수식, 동영상 지원
- 첨부파일
- 인쇄 최적화
- 오류 신고 또는 문의하기 연결

초기에는 하나의 매뉴얼 게시물로 시작할 수 있어야 합니다. 분량이 커질 경우에도 글로벌 메뉴 구조를 변경하지 않고 내부적으로 하위 문서를 확장할 수 있게 설계하세요.

확장 URL 예시:

```text
/resources/pf3d-manual
/resources/pf3d-manual/getting-started
/resources/pf3d-manual/modeling
/resources/pf3d-manual/analysis
/resources/pf3d-manual/results
/resources/pf3d-manual/troubleshooting
```

하위 문서가 생겨도 사용자는 기술자료 목록에서 `PF3D 사용 매뉴얼` 게시물을 선택해 진입해야 합니다.

Markdown과 MDX, Git 기반 관리와 CMS 기반 관리를 비교하고 MVP에 적합한 방식을 선정하세요. 운영 방식이 확정되지 않았다면 Git 기반 MDX와 front matter를 우선 검토하되, 추후 비개발자용 CMS를 연결할 수 있도록 콘텐츠 접근 계층을 분리하세요.

PF3D front matter에는 다음 필드를 검토하세요.

```yaml
title:
description:
slug:
category:
order:
version:
status:
visibility:
keywords:
updatedAt:
relatedDocuments:
```

- 요약
- 본문

필요한 경우 콘텐츠 유형과 PF3D 버전 필터를 제공합니다. 한글 검색, 부분 일치, 검색어 강조, 결과 문맥 미리보기, 검색 결과 없음 상태를 고려하세요.
